# Complete writing journeys

Required alpha.3 UX tasks, derived from the existing PT scenarios and explicit feedback; **not observed research sessions or passed native tests**. Capability completeness remains separately mandatory. Six tasks do not exhaust the source inventory. The exact requirements and evidence joins live in `docs/migration/PARITY_SCOPE.json` and the existing `UX_GATE.json.coverage`; there is no second independent approval authority.

## PT-MIG-01 — continue an existing project

As an existing Studio writer, I need my old work to remain usable so that changing applications does not interrupt the manuscript. Start with a synthetic old/custom project containing hierarchy, revisions, notes, dictionary/context, boards and original media. Import; find those objects; edit a document and board; save/restart; export reader Markdown with artifacts and separately restore a canonical copy. Return to the intended document/card with stable identity. A corrupt/missing asset, duplicate import, cancelled transfer or failed write must not damage the original or report a partial copy as success. Compare semantic data, unknown fields, original bytes and references. Baseline #10/#11; the private reference stays local and read-only.

## PT-NOV-01 — restructure without losing the writing context

As a prose writer revising a long draft, I need to move a scene and continue at the same passage. Start with two chapters, repeated text, a linked note and a source reference. Open the scene; write; move it to a valid parent; inspect its retained references; enter bounded Focus; save/reopen and resume. Keyboard and pointer paths share authority. Cancel/invalid nesting/stale tree/save failure retain the previous structure and unfinished writing. PT-FOCUS-01 is part of this journey. Existing hierarchy/editor requirements are mandatory; a new genre selector or template is not validated by this task.

## PT-EDIT-01 — make and review an exact editorial change

As an editor working with an author, I need a note/proposal to address the intended occurrence and respect later edits. Mark the second identical passage, attach a note, prepare a real supplied proposal and inspect it; change the source before applying. Show the stale state, reject or obtain a fresh exact proposal, Apply and guarded Undo; reopen. Preserve formatting, anchors, note updates and later text. Return to the exact passage after inspecting notes/context. Cancelling or failed persistence must not apply a proposal. Baseline #2/#4; scripted local suggestions are not model output and no collaboration service is implied.

## PT-NONF-01 — compose an illustrated chapter

As a nonfiction writer, I need images and tables to communicate alongside text and survive handoff. Start from an empty chapter plus an original source asset; insert an image/caption and a table, edit content and supported dimensions, cancel one resize, Undo/Redo another, save/reopen, export a readable chapter with real artifacts. Return from properties/export to the same object/passage. Missing assets, stale edits, narrow layouts and failed output remain actionable without overlap or data loss. Block authoring/preservation are baseline; direct sizing is explicitly requested #14. Additional Word-style publishing features and unselected sizing semantics remain discovery, not implicit requirements.

## PT-KNOW-01 — consult lore while revising

As a writer checking continuity, I need dictionary/guide/memory context without losing my place or confusing its authority. Start with a marked passage linked to a term and scoped context records. Follow the exact reference, inspect/edit the intended record, distinguish a saved snapshot from current content and return to the original caret/scroll. Rename/trash/restore, detached reference, cancelled edit, stale revision and failed save preserve records/history and explain unavailable targets. Save/reopen and transfer must preserve identity; title/quote similarity must not guess links. This uses existing domain behaviors, not an unselected automatic consistency assistant.

## PT-LINK-01 — move between planning and scene writing

As a narrative planner, I need the board and manuscript to support the same scene. Start with a free note, an existing document card and a scene containing repeated passages. Write in the card; use the existing document reference or explicit promotion; revise/save the intended scene; return to the original board pan/zoom/selection and manuscript context. Rename/move/trash/restore the target; reopen and transfer (PT-LINK-02). Layout-only moves must not reorder or edit the manuscript. Cancel, failed save and stale/missing target preserve drafts and provide a return path. Existing references/promotion/types are #17 baseline; new synchronization/backlink/entity models under #14 require recorded selection and verification. A type called Screenplay does not establish professional screenwriting readiness.

## Evidence and research rules

For every task, record the exact fixture, application source/lock fingerprint, platform/build, native entry/actions, observed outcome, context before/after and failure/cancel/stale/reopen cases. Include independent verdict and actionable findings. Hash the report after review; mutable prose or two screenshots cannot substitute for the interaction record. Public evidence uses synthetic data.

Each research finding separately records: evidence kind (direct request, observed session, first-hand public report, vendor documentation, or design inference); source/date; hypothesis; contrary case; selected/rejected/pending decision; criterion and observed result. Competitor documentation proves documented behavior only. Engineer-authored personas are hypotheses until exercised with people; neither their existence nor passing automation is user validation. Preserve existing H-LINK and PT IDs and decisions. Do not implement unselected ideas, remove legacy behavior for a prettier demo, or call a cumbersome complete checklist good UX.

Full-product recording/transcription creation, provider connectivity/released MCP transport and publication formats retain their existing boundaries in FEATURE_PARITY/NEXT_RELEASE; this selected alpha.3 gate does not assert those separate workflows are complete. A later expansion must add their capabilities and journeys before claiming broader parity.
