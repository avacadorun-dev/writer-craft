# Desktop workflow map

Scope: translate the complete Writers Studio author workflow into WriterCraft's desktop model. This is a design contract and acceptance inventory, not an implementation-completion claim. See [feature parity](../migration/FEATURE_PARITY.md), [desktop contract](DESKTOP_UX.md) and [UX gate](UX_ACCEPTANCE.md).

The first full platform is macOS. Main writing uses continuous text within a bounded editor pane; navigation and inspectors remain stationary. Publication pagination is a separate mode. SolidCraft informs compact utility composition, not author vocabulary or CAD information architecture.

## Stable application model

One application shell owns project identity, current central work surface, navigator, optional peer inspector and activity/status. Central surfaces are Manuscript, Canvas, Project overview/search, Audio/Transcript review and Publication preview. Secondary tools return to the source document/board with caret, selection, scroll and camera state retained. A mode switch is explicit; browser Back/Reload and URL routing are not the navigation model.

Keep context consistent across surfaces: project ID/schema, document/board ID, base revision, current selection/scope, draft/save state and active recording/run. Do not infer an AI edit target from whichever text happens to be visible later. Large task-specific review uses the center; ordinary information/actions remain in the appropriate inspector. Do not add one permanent panel per feature.

## Component and context rules

The author should not manage the app's internal modules. Use progressive disclosure and consistent command locations. Keep application shell, navigator, manuscript surface, inspector views, settings and recovery presenters independently understandable and testable. Route their actions through a workspace controller/shared domain commands.

Every transition records the origin (document/board, selection/caret, scroll/camera and pane arrangement). Context remains attached to its original occurrence even after focus moves. Heavy operations run off the rendering thread with cancellation; saving original text/audio has priority over network/provider work. A viewer/preview must not be labelled as completed migration.

## Parity acceptance examples

- Repeat a character name in two paragraphs. Select the second, add a note, edit the first and the text before the second; note still refers to the second. Delete its quote: note becomes detached, not attached elsewhere. Undo restores the intended note/range.
- Dictate while the provider disconnects, pause, manually edit the draft, finish, restart and inspect audio/text. Original capture and manual work survive; late recognition is reviewable.
- Open a linked manuscript from a board, inspect an annotation and return. Board camera/selection and manuscript caret/draft remain recoverable.
- Run an assistant change against a selected scope, edit manually while it works, then review. Proposal scope/staleness is understandable before Apply; no later author text is overwritten.
- Change language/theme at a small laptop window while a draft exists. Controls remain reachable and the draft/selection is unchanged; restart retains preferences.

Each implemented row needs concrete OpenSpec scenarios, native interaction/visual evidence and independent design acceptance. This map supplies placement and invariants; it is not sufficient evidence by itself.

## Shared shell geometry correction — F-19

Toolbar identity and navigator are separate components with one shared layout boundary. Resizing, hiding or adaptively replacing the navigator updates the matching toolbar identity zone. Allocate a bounded title region before placing neighboring controls; truncate with access to the complete title instead of overlapping labels or reducing utility hit targets. Reviewers must compare these components together in compiled narrow/common/wide and long-title captures. This implements the owner's observed alignment correction and changes no author feature scope.
