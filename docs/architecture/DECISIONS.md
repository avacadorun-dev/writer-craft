# WriterCraft architecture decisions

Accepted decisions as of 2026-11-07. Each records an actual chosen direction and consequence. Replacing one requires a new ADR that names the superseded decision; do not silently rewrite history. Implementation or release verification remains tracked in the active change.

## ADR-001 — Native Rust application with shared core

Status: accepted. Context: the product is moving from server deployment to a desktop authors install directly. Decision: use Rust application code, egui/eframe native rendering and a GUI-independent command core shared with CLI and future MCP. Alternatives considered: retain a browser shell; wrap existing UI in Tauri; rewrite every subsystem immediately. Consequence: installation can avoid the server stack, while the editor and native accessibility require real implementation and validation. A Rust text widget is not rich editing parity.

## ADR-002 — Local SQLite, immutable revisions and durable drafts

Status: accepted. Context: current persistence uses PostgreSQL/S3 and browser recovery. Decision: local SQLite with foreign keys, WAL, FULL synchronous mode, bounded busy timeout and immediate write transactions; append document revisions and capture unfinished drafts separately. Versioned additive migrations reject newer schemas and foreign databases. Alternatives: bundle database/storage servers; save only ad-hoc text files; overwrite a single current snapshot. Consequence: users need no database administration; long I/O must leave the render thread, and power-loss/backup guarantees need separate evidence.

## ADR-003 — Proposal staging is separate from commit authority

Status: accepted. Context: suggested edits must preserve authorship and concurrent manual writing. Decision: exact expected text and Unicode-scalar anchors; separate before/proposed snapshots with integrity hashes; explicit Apply/Reject; atomic base checks; compensating Undo guarded by the applied revision/body. Alternatives: direct provider writes; text-matching without revision checks; unconditional restore. Consequence: ambiguous/stale operations fail visibly, and newer work survives undo conflicts. Multi-document groups remain later work.

## ADR-004 — Preserve imported structure before editable migration

Status: accepted. Context: legacy transfer versions1–8 contain editor schemas1–4, histories, audio/assets, annotations, Canvas and context. Decision: bounded read-only ZIP inspection first; retain complete supplied JSON and original archive; imported rich preview stays read-only. Alternatives: flatten every document to plainText; claim a full import from partial DTO parsing; copy server storage into the installer. Consequence: initial import usefulness is limited but data is preserved. Full migration needs reference mapping, atomic asset/database staging and semantic round-trip tests.

## ADR-005 — Independent brightness and non-green palette identity

Status: accepted product direction; implementation acceptance pending. Context: sustained writing requires Light/Dark and requested legacy themes. Decision: one semantic token system with separate brightness and palette IDs; retain cedar-and-copper, dried-rose-and-wine, fog-graphite, linen-clay, dusty-lavender and porcelain-ink; native charcoal/blue remains available. Exclude green-accent quiet and olive-ink. Alternatives: a single hardcoded dark theme; couple each palette to one brightness; restore excluded palettes. Consequence: preferences and every panel/dialog must consistently resolve mode/palette; pairwise visual acceptance is required.

## ADR-006 — Incremental native delivery, complete parity target

Status: accepted. Context: a complete rewrite spans rich editing, audio, Canvas, assistants and publishing. Decision: deliver a bounded plain-prose MVP with an explicit parity inventory, then migrate complete workflows against acceptance fixtures. Alternatives: freeze delivery until a full rewrite; announce equivalence from a basic editor. Consequence: limitations are visible, original projects stay unchanged, and release claims depend on passing workflow evidence.

## ADR-007 — Repository-local OpenSpec change contracts

Status: accepted. Context: agents need durable product intent and bounded changes beyond chat history. Decision: adopt [OpenSpec's default artifact structure](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml), [config conventions](https://github.com/Fission-AI/OpenSpec/blob/main/docs/customization.md) and WHEN/THEN capability scenarios, connected to PRD, ADRs and named test evidence. Alternatives: chat-only requirements; parallel unmaintained planning frameworks; a heavyweight custom process. Consequence: manual bootstrap is useful immediately; official CLI initialization/validation must be recorded honestly when executed. Existing user authorization remains valid throughout the workflow.

## ADR-008 — External reusable engines, internal writing domain

Status: accepted. Context: rich editing, text layout, document formats, transcription runtimes and other substantial generic engines can outgrow a single application's business code. Decision: prefer a maintained existing specialized library. When new generic engine work has a real reuse boundary and substantial independent functionality, develop it in a separately versioned repository with its own API, tests, documentation, provenance and releases; WriterCraft consumes a pinned package/revision through a narrow adapter. Keep WriterCraft project/manuscript invariants, review authority, workflow policy and application commands in this repository. Alternatives: copy a large generic engine into business modules; split every helper into a repository; create speculative packages with no current consumer. Consequence: current domain crates stay internal, no speculative new repository is required, and a future extraction must identify an actual reusable contract and maintenance owner before it changes dependencies.

## ADR-009 — Eight built-in UI languages with explicit source preservation

Status: accepted product requirement; integrated acceptance pending. Context: the native MVP must support Russian plus seven additional interface languages immediately. Decision: bundle ru/en/de/fr/es/pt/zh/ja catalogs, switch semantic messages live, persist the selected language, and provide offline CJK glyph coverage. Keep manuscript/user titles/quotes unchanged and identify original technical diagnostics separately. Missing/invalid preferences use Russian with an actionable visible recovery state; unknown translation keys expose a neutral diagnostic rather than silently showing Russian in another locale. Alternatives: remote runtime translation; partial labels; translating stored user content; postponing internationalization. Consequence: catalog/parameter tests, hardcoded-string review and native CJK/layout verification are release checks, not assumptions.

## ADR-010 — macOS first full desktop release

Status: accepted product rollout. Context: native integration, fonts, installers and interaction behavior need direct platform evidence. Decision: deliver and verify the first full desktop release on macOS; keep the core portable and its CI useful, then add Windows/Linux desktop delivery with their own UI, dialog, accessibility and installer acceptance. Alternative: imply simultaneous three-platform readiness from a portable Rust build. Consequence: current releases name actual platform support, while platform-specific adapters remain separate from writing-domain rules.

## ADR-011 — Continuous manuscript writing, publication-stage pagination

Status: accepted product interaction. Context: authors compose and revise long text within one bounded writing workspace. Decision: use a continuous text flow with editor-local scrolling; pagination and page-size/margin layout appear in publication preview/export. Alternative: split the primary writing surface into simulated paper pages. Consequence: editor structure follows writing operations and stable document identity; print layout is a later rendering concern and must not redefine canonical text or caret behavior.

## ADR-012 — Separate native rich editor with original canonical semantics

Status: accepted implementation direction, 2026-11-08; full editor acceptance pending. Context: the owner selected all current original editor behavior for alpha.2, including future MCP command equivalence. A plain text widget, preserved JSON or reduced rich-text subset cannot establish the product hypothesis. Decision: develop reusable native document/model/view mechanics in the separate CraftEditor repository; pin reviewed commits through narrow application adapters. Preserve the original PM-shaped canonical JSON with explicit typed positions and exact revisioned transactions. Keep WriterCraft projects/storage/media authorization, note/dictionary semantics and assistant review here. Reuse focused existing Rust validation/layout/input components after qualification; do not vendor a full word processor or replace canonical data with a lossy renderer model. Alternatives: isolated per-block fields, Markdown/source-only editing, direct WordCraft model replacement, DOM/WebView view. Consequence: model and storage checkpoints are useful but cannot pass `full-editor-parity`; complete native input/render/integration evidence remains mandatory. See `docs/research/EDITOR_ENGINE_DECISION.md` and the full source/UX matrices. This implements ADR-008's real component boundary rather than extracting speculative helpers.

## ADR-013 — Native rich-block rendering and sealed edit provenance

Status: accepted implementation architecture, 2026-11-08; complete alpha.2 acceptance remains pending. Context: the full editor requires real diagrams, images and inline/display formulas in the same native flow, plus exact passage-note mappings through debounced saves and Undo. Decision: use the separate CraftEditor renderer service with pinned Merman, RaTeX and resvg libraries; prepare actual raster output and measured bounds on a host worker, then supply an immutable generation-aware catalog to the WordCraft layout/raster projection. Host-authorized media bytes and localized failure labels cross a narrow resolver boundary; canonical source never becomes a bitmap or a guessed paragraph. Formula baselines come from actual layout metrics. Preserve source-compatible formula restrictions and explicit source fallback on rendering failure. Keep underlying dependency/font notices in distributions, including ELK and KaTeX materials.

Native edit batches carry immutable, non-deserializable model replay proofs. The application replays typed commands against its guarded canonical base and compares the exact resulting structured tree before committing text and note mappings in one SQLite transaction. Undo/Redo attachment restores use exact retained history receipts, rather than matching JSON or searching for a quote. Failed commits retain pending proofs and drafts. Recovered snapshots without their original receipt journal use an explicit recovery path with conservative attachment handling; complete draft/recovery/native acceptance remains required.

Alternatives: browser Mermaid/KaTeX runtime, pre-rendered demonstration images, arbitrary public position maps, full-document text matching, or rendering every atom on every prose keystroke. Consequence: reusable rendering/provenance mechanics stay in CraftEditor, while WriterCraft owns media authorization, persistence and author workflows. The first engine checkpoint passed 137 hosted model/view/renderer tests and real PNG examples; this does not prove complete syntax, animation, inherited formula typography, native input or application parity. See `docs/research/NATIVE_BLOCK_RENDERERS.md`.

## ADR-014 — Pinned directory capabilities for portable-folder input

Status: approved for alpha.3 qualification, 2026-11-09; exact dependency/lock resolved on a hosted runner, compiled folder acceptance pending. Context: canonical Markdown/artifact folders must read only the selected root, reject symlink members/parents and verify every declared file before any project becomes visible. A check with `symlink_metadata` followed by ordinary ambient `File::open(path)` cannot itself bind the later open to the checked directory on every supported platform.

Decision: qualify exactly `cap-std =4.0.3` with default features disabled for the transfer adapter. Grant ambient authority once to the user-selected root using `Dir::open_ambient_dir`, then resolve member traversal/open operations through owned relative directory capabilities. Reject noncanonical paths, symlinks/reparse members and nonregular payloads; inventory actual files and enforce file, shard, total-byte and cancellation bounds. Freeze verified bytes into the existing private core index before semantic restoration. Keep the original `.wstudio` archive adapter unchanged. Do not create private unsafe Unix/Windows filesystem wrappers.

The [versioned package manifest](https://github.com/sunfishcode/cap-std/blob/v4.0.3/cap-std/Cargo.toml) declares edition 2021, empty default features and `Apache-2.0 WITH LLVM-exception OR Apache-2.0 OR MIT`; preserve all required transitive notices rather than changing the application license. Production dependencies include `cap-primitives`, `io-extras`, `io-lifetimes` and filesystem `rustix` on non-Windows. Its package manifest does not declare an MSRV; qualify against WriterCraft's exact hosted compiler/platform matrix and retain the resolved lock/dependency report before claiming compatibility. No local Cargo resolution/build is authorized for this change.

The [Dir contract](https://docs.rs/cap-std/4.0.3/cap_std/fs/struct.Dir.html) defines relative capability operations and warns that `from_std_file` needs a correctly opened Windows handle. Use the explicit ambient-root constructor instead of wrapping an ordinary share-delete-enabled file handle. The [upstream design](https://github.com/sunfishcode/cap-std/tree/v4.0.3) confines resolution beneath an opened directory; static member/type checks remain required by WriterCraft's stricter completed-folder contract.

Alternatives: ambient path checks only; handwritten unsafe platform traversal; reintroducing ZIP-only backups without the required Markdown/artifact workflow. Consequence: an established filesystem component owns platform traversal mechanics; WriterCraft still owns completion manifests, exact file/hash/scope verification, resource budgets, cancellation and atomic project semantics. Acceptance needs actual static symlink/ancestor rejection, root rename/path substitution, changed-reading-file refusal, corruption/cancellation rollback and target-platform tests. The exact resolved graph and license declarations are recorded in [capability dependency qualification](CAPABILITY_FOLDER_DEPENDENCY_ALPHA3.md). This ADR does not claim that compiled folder behavior or the complete folder UI is accepted.

ADR-014 refinement (2026-11-09): independent source review requires same-version disabled-default `cap-fs-ext` public no-follow/nonblocking option traits and an actual opened-handle regular-file check, not path metadata as later-open authority. FIFO/special-file substitution must fail without waiting for a writer. Regular file/control/marker bytes and file counts share one stage-aware budget; relative directory count has its own identical writer/scanner guard and is not charged as a regular file. The completion receipt excludes the removed marker. See the dependency qualification and deterministic replacement/budget contracts; compiled/native acceptance remains pending.

## ADR-015 — Maintained native React Flow capability in CraftCanvas

Status: selected direction, 2026-11-09; production and interaction acceptance pending. F-47 rejects the current connection UX and F-48 prioritizes a standalone production library with full functional React Flow parity before further WriterCraft Canvas integration. This extends ADR-008 and preserves ADR-001/002/003.

Decision: retain CraftCanvas's guarded canonical model, precision and preservation machinery; develop the generic port, interaction, rendering and host-composition API against an exact React Flow baseline. Use qualified upstream algorithms and source references selectively, with provenance and license notices. Do not adopt egui-xyflow unchanged, upgrade all egui consumers to follow it, or replace canonical JSON with its mutable graph. Delivery must not wait for upstream maintenance. See [the source comparison](../research/NATIVE_CANVAS_INTERACTION.md) and the separate engine production plan.

React Flow 12.12.1 at `1bc405cd113618c17fd181b931a9fe573bec9fee` is the initial library comparison baseline. Original Studio's frozen source inventory remains a separate consumer contract. Native functional equivalents cover component/DOM mechanisms through Rust host hooks and native accessibility; reactivity syntax is not an API compatibility promise. Full capability coverage, named/dynamic ports, controlled lifecycle events, custom rendering, viewport/selection, input ownership and accessibility must be assessed before stabilizing the API. A four-midpoint connection patch is insufficient architecture for this goal.

Alternatives inspected: egui-xyflow, egui-snarl, egui_node_graph2 and egui-flow-editor. Their compatibility, authority, endpoint identity or implemented-interaction gaps prevent unchanged adoption. The useful native interaction work is reference material, not evidence of production equivalence. No new runtime dependency or storage migration is selected here.

Consequences: generic capability and release qualification belong to CraftCanvas; WriterCraft retains project/media authorization, catalogs, persistence acknowledgements, schemas, manuscript relationships and complete B01–B26 journeys. Both engine readiness and consumer acceptance are mandatory. Other product implementation is parked under F-48; current preview and retained drafts remain untouched.

## ADR-016 — Structured writing metadata and older-writer protection

Status: selected for bounded alpha.3 qualification, 2026-11-09; native acceptance pending. F-49–F-51 authorize the non-Canvas hierarchy, passage markup and reference workflow in #14. Reuse the original free folder/document/note schema for native projects and retain imported schemas. Core guarded transactions own tree mutations, stable resource aliases and recoverable subtree deletion; manuscript bodies and document history are not tree ordering storage. Character descriptions and motivations are ordinary authored documents, not a new nominal project taxonomy.

Add exact author-defined tags to existing annotation JSON with an empty default for older records. Existing annotation anchors, revisions, histories and canonical transfer remain authoritative. Bump the workspace schema from 9 to 10 without rewriting rows so older binaries refuse the workspace before they can discard fields on save. This opener boundary cannot protect an older process already connected to the same database; candidate validation uses isolated workspaces. Older released installers and their data remain untouched.

Portable format 2 remains additive: this build reads older exports and retains unknown data. Older readers preserve unknown note extensions as evidence but do not support editing new tag semantics or guarantee their automatic rehydration after an old-app round trip. Do not advertise downgrade editing as compatible. A metadata-only migration regression compares exact annotation/history bytes; semantic transfer tests cover tags and anchors in the current build.

Alternatives: fixed character/project-type selectors without a validated workflow; inline tags in canonical prose; silently permitting old annotation writers; a new generic tree dependency. The selected design keeps application workflows here and does not change Canvas/editor engine pins.

## ADR-017 — Reusable project label colors and compatible tag identity

Status: selected for F-54 implementation and qualification, 2026-11-09; native acceptance pending. The existing exact tag strings are already user-authored assignment identities. Replacing them with a new entity taxonomy or rewriting annotation history is unnecessary for the requested reusable colored labels.

Decision: retain exact, case-sensitive tag names and ordered annotation assignments. Add a guarded project catalog with named color values (Blue, Violet, Rose, Orange, Amber, Gray), including unused and retired definitions. The application maps these semantic values to restrained accents compatible with each appearance/palette; RGB values do not become manuscript content. The first assigned label supplies the primary mark color, while all assignments remain named chips. Overlapping marks use an explicit presentation priority with canonical identities retained, not a mixed color with a new implied meaning.

Workspace schema 11 adds a separate extensible catalog table and prevents schema-10 writers from desynchronizing shared definitions through old tag commands. Opening older workspaces does not rewrite annotation/history JSON; missing legacy definitions have a compatible Blue presentation default and are persisted only through deliberate mutation. The original imported source manifest remains unchanged. Current canonical format 1/2 paths retain the catalog, including unused/retired definitions and unknown extension fields; older readers are not qualified to edit or round-trip the new semantics.

Create and recolor compare a captured catalog revision. Rename guards the complete reviewed active/deleted occurrence set and atomically updates current assignments and the definition, preserving exact anchors, text and prior history. Color-only edits change no document or annotation revision. Remove retires the definition, unlinks active assignments and preserves recoverable tag-only marks. Retired names remain reserved: reuse requires explicit restoration retaining the prior color. Restoring a deleted mark may restore its retired label definitions with disclosure. No operation guesses attachment from matching words or merges differently authored names.

Consequences: label catalog changes independently invalidate presentation caches even when manuscript/note revisions stay unchanged. Pending note drafts must remain intact through catalog refresh and must be reviewed before bulk assignment changes. Domain/portable preservation tests and a new exact native author journey are required; no editor/Canvas dependency change is needed for host-owned decoration colors.

Selected-document canonical exports retain only definitions referenced by included current annotations or their history; unrelated unused vocabulary belongs only in complete-project exports. Unknown fields on included definitions stay intact. Unscopable unknown catalog-level fields cause an actionable complete-project fallback before output instead of leaking unrelated metadata or discarding unknown data. Historical tag names remain exact; the catalog describes current colors and does not invent historical colors for renamed labels.
