# Evidence, scenarios and compatibility boundaries

Start with docs/research/PROJECT_TYPES_AND_FORMATTING.md and existing source/parity contracts. A vendor feature page supports a documented comparison, not a population demand claim. First-hand requests, actual observed tasks, assumptions and product hypotheses have different evidence status. Record evaluated versions, dates and unobserved cases.

Treat the kind/template/editing-mode/output separation as a hypothesis, not a predetermined architecture. For each proposed distinction, state which behavior changes, why it benefits the task, what stays configurable and how the author can recover or change course. New profiles must not make imported custom hierarchies or mixed research/manuscript documents unusable.

A scenario record has stable ID, status, role/job, evidence and hypothesis, start state, trigger, primary sequence, observable outcome, alternatives, cancel/stale/error/recovery, migration and exact artifact expectations. Trace research→requirement→OpenSpec→issue/implementation→semantic/native/independent UX evidence. Written scenarios and source tests are not observed native acceptance.

Direct resizing must distinguish workspace zoom from stored object size and publication size, manuscript flow from free Canvas coordinates, and live preview from acknowledged mutation. Original image/source bytes and supported Studio fields survive. Version any new semantics and provide compatible defaults/migration; preserve unknown original data. A completed gesture is a guarded atomic edit with cancel and Undo.
